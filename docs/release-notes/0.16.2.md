# Benchy 0.16.2

This release fixes unattended Windows machines that never ran a scheduled test needing administrator rights or a machine-wide install. It goes with engine 0.14.1 and client 0.17.1.

## Waiting for an acceptance is now visible

A test like that has to be accepted once, at the machine, before the server will send it. The server used to say a schedule was waiting for that only while the schedule was due, so between runs nobody could see it and nothing could be accepted ahead of time. Now the server tells the machine what is waiting on every check-in, so the desktop client can show it and offer to accept it straight away, with one administrator prompt for any number of tests.

The server's own pages say it too. A schedule's page has a line at the top such as "Held on 1 of 2 machines: needs acceptance at the machine (Title 1.2.0)". The systems list marks a machine that is waiting with "Needs acceptance", and the main page counts them. Nothing is stored for this; it is worked out when you open the page.

Older engines and clients are unaffected: they get the same information in the same shape and show it as they always did.

## Updating the server from its web page

Until now, updating a Benchy server meant a shell on the server and root. From 0.16.2 the server administrator can do it from **Server settings**, in a new **Server updates** section.

A server update is a signed bundle, `benchy-server-update-X.Y.Z.zip`, with the new `benchy` and `benchy-server` packages in it. It is on every Benchy release on GitHub from 0.16.2 on. Press **Check GitHub** and the server fetches the newest bundle (and the one for the version it runs now, which it keeps as the way back), or upload the file yourself, or import it on the server with `benchy server-update-import FILE`. The server checks the signature against the key table it already has for engine updates, so a bundle from anywhere else is refused and nothing new has to be trusted.

When a newer bundle is held, an **Update to X.Y.Z** button appears. You enter your password again to confirm it. If machines are in the middle of a test run, the page lists them and asks for a tick: their results upload once the server is back. Then the server restarts and the page follows it. The web process never gets root. It only writes a small request file; a separate update service (`benchy-server-update`, started by a systemd path unit) reads that request, checks the signed bundle again from scratch, copies the database, installs the two packages, starts the server and checks that it runs the new version with the new database schema. If any of that fails, it puts the previous version and the database copy back by itself and says what went wrong on the page. An older or equal version is never installed from the page.

This works on servers installed from the `benchy` and `benchy-server` packages. Anything else (a source install, Windows, the rpm) shows the command to run instead of the button. seinar moves to the packages once, with `deploy/deb-package/move-to-deb.sh`; the first update you can do from the web page after that is the one after 0.16.2.

0.16.2 itself is installed the usual way: `sudo apt install ./benchy_0.16.2_all.deb ./benchy-server_0.16.2_all.deb`. That also turns on the update service. Server administrators only: a user who is only an account administrator sees nothing of this.
